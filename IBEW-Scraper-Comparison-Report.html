Scraping Pipeline Flow

source analysis

⚡ v3 Pipeline

master.json → Crawl URLs → ML URL Classifier → Platform ID
Per-local scraper → Puppeteer/Selenium → Extract jobs
ML NER (spaCy) → jobCrud.js → Firestore
⚠️ No normalization layer — each scraper outputs its own JSON shape. No dedup key. No empty-string convention. No eval framework.
✅ ML pipeline is unique — spaCy NER model trained to extract job fields (company, wage, classification, etc.) from raw text. URL classifier (SVM) categorizes crawled URLs.

🌐 Trampbook Pipeline

Catalog (244+) → tvly map → URL seeder (BM25) → Platform adapter
Cheerio parse → Normalize → buildDedupKey()
Drizzle ORM → MySQL → Push/SMS/Email
✅ Normalized schema — NormalizedJobListing with empty-string convention, buildDedupKey(), Eastern TZ ISO-8601. All adapters output the same shape.
ℹ️ Hybrid pipeline scaffolded but not yet production — scripts/hybrid/ has core/, profiles/, runners/, normalize/ dirs but they contain only .gitkeep files. The plan exists (plan.md P2-P5) but isn't executed yet.

🔑 Key Insight: ML vs Pattern-Matching

v3's ML pipeline (spaCy NER + SVM URL classifier) is genuinely innovative — it can extract structured data from any HTML without writing platform-specific parsers. Trampbook relies on handwritten Cheerio parsers per platform, which is more reliable for known platforms but can't handle unknown ones. However, v3's ML is not integrated into its production scrapers — it's experimental code sitting in machine_learning/ while the actual scrapers (completed/*.js) use hardcoded Puppeteer selectors.

Recommendation: The Best Path Forward

actionable

💡 The Winning Move: Port v3's ML into Trampbook

The two projects are complementary. v3 has the ML pipeline that Trampbook needs; Trampbook has the scalable architecture that v3 lacks. The ideal path is to port v3's spaCy NER model and SVM URL classifier into Trampbook's adapter framework as a fallback adapter — the "generic ML adapter" that runs when no platform-specific adapter matches.

⚡ v3 — To Make Production-Ready

  • Rotate/secrets immediately — BrightData creds + Firebase key + OpenAI key are compromised in git history
  • Move to .env — all credentials must come from environment variables
  • Integrate ML into runAllScrapers.js — the spaCy NER and SVM URL classifier exist but aren't used by the production scrapers
  • Add a normalization layer — all scrapers should output a common schema (copy Trampbook's NormalizedJobListing)
  • Add deduplication — buildDedupKey() equivalent to prevent duplicate job postings
  • Scale beyond 7 locals — the per-local approach doesn't scale to 244+. Need platform detection + adapter pattern
  • Replace 169 print() calls — use Python logging module
  • Add cron scheduling — manual runAllScrapers.js is not sustainable
  • Remove vendored Crawl4AI — install via pip, don't ship the full library in the repo
  • Estimated effort: 3-4 weeks to reach Trampbook's level

🌐 Trampbook — To Add ML Capabilities

  • Port v3's spaCy NER model — install as a Python service, call from the generic adapter as an ML fallback
  • Port v3's SVM URL classifier — use it in the URL seeder (scripts/hybrid/core/) instead of pure BM25 keyword matching
  • Complete the hybrid pipeline — scripts/hybrid/ has the directory structure but only .gitkeep files; implement P2-P5 of plan.md
  • Refactor parseUnionActiveTable — cognitive complexity 165 with 8 loops is the worst function in either project
  • Split jobCallsScraper.ts — the 11 parsers in one monolith should be individual adapter files
  • Add BrightData proxy support — for the ~4 UnionWorx SPA boards that need client-side rendering (optional, store creds in .env)
  • Wire fabrication scan into CI — the eval framework exists but isn't automated
  • Estimated effort: 2-3 weeks to integrate ML + complete hybrid pipeline
